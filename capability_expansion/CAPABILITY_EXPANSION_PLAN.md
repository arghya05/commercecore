# CommerceCore capability expansion plan

Source context reviewed before writing this: `ecommerce/Commerce_SLM_Research_Plan.md` (the CommerceCore-specific plan that was actually executed and produced the shipped model — read in full, all 484 lines), the deployed repo `github.com/arghya05/commercecore` (cloned locally at `commercecore/`, read in full including README, schemas, training results, and model-selection decision), and `additonal/Retail_Ecommerce_SLM_Research_Source.md` (a separate, much broader 5,777-line "retail intelligence" report — 77 papers, 67 model repos, 40 datasets, 35 chapters — now read in full after an earlier pass only sampled it; see §0 below for what it changed).

This plan reconciles **three distinct sources that each propose a different task decomposition**, not one document restated three ways:
- The user's 9-capability table (Retrieve/Understand/Match/Query/Rank/Taste/Bundle/QA/Agent) — the target this plan is organized around.
- `Commerce_SLM_Research_Plan.md`'s own 4-module framing (query intent → catalog/taxonomy → retrieval/matching → search recovery/tools) — this is what actually shipped (Commerce-Query only).
- The broader dossier's own recommendation (its ch. 1, 24, 33): a **different 4-task FashionDecision product** (`extract_product`, `parse_need`, `verify_candidate`, `extract_return_issue`) on the same Qwen3-1.7B, plus three parallel "Product A/B/C" groupings (catalogue quality / discovery intelligence / policy-grounded assistant) that map loosely, not exactly, onto the 9-capability table (Product A ≈ Understand+Match, Product B ≈ Retrieve+Rank+Query, Product C ≈ Agent; Taste/Bundle/QA have no direct analog in that framing).

Where these three sources conflict, this plan is organized around the user's 9-capability table and treats the other two as evidence/cross-checks, not competing plans to merge by force.

## 0a. Clear separation: the shipped GitHub repo vs. this expansion — and what the two together cover

Confirmed requirement: there must be a clear, unambiguous separation between the shipped `github.com/arghya05/commercecore` repo and this expansion, and the two together must cover the full shopper-facing ecommerce use-case surface with no gap between them — not two disconnected efforts, but one continuous, non-overlapping build.

**What the shipped GitHub repo owns, and only this — never touched, never expanded in place:**
- One capability: **Commerce-Query** (shopper intent/constraint extraction).
- One artifact: the step-750 QLoRA adapter merged into `models/commercecore_merged_step750/`, published at `huggingface.co/arghya2030/commercecore-qwen3-1.7b`.
- One serving surface: `serve/api.py`'s existing `/parse-query` route.
- This boundary is absolute per §2b: no retraining, no resuming, no overwriting, ever, regardless of what else this expansion builds.

**What this expansion owns, entirely new, never inside the shipped repo's own training/serving path:**
- The other eight capabilities (Understand, Match, Retrieve, Rank, Bundle, Agent, Taste, QA), each as either a sibling adapter sharing only the frozen base weights, or a fully separate model (§1b, §2b).
- The four real gaps found in §2h (entity dedup, exact-model compatibility, session memory, review synthesis) — each folded into one of the eight above, not a 10th capability.
- All new code lives in new files/directories alongside the shipped repo's existing structure (`00_expansion_core.md`'s repo layout) — additive, never replacing what's there.

**Combined coverage claim, checked against §2h, stated precisely so it can be verified rather than asserted:** the shipped repo (Commerce-Query) plus this expansion's nine-capability portfolio together cover the **shopper-facing discovery and understanding surface** of ecommerce — query interpretation, catalog understanding, product matching/deduplication, retrieval, ranking, personalization, bundling/compatibility, grounded product Q&A, and read-only agentic search execution. This explicitly does **not** claim coverage of the transactional/operational surface named in §2h (order status, returns, payments, fraud, warehouse/store-operations, pricing/BI) — that is a different product, correctly out of scope, not an unaddressed gap in what these two together promise to cover. If "all use cases of ecommerce" is meant to include that transactional/operational surface, that is new scope beyond both the shipped repo and this expansion, and would need its own plan, its own data-partnership decisions (most of U31–U60 need owned transactional systems, not public datasets), and its own build — it should not be silently absorbed into this portfolio's claims.

**Decision, confirmed:** the transactional/operational surface (U31–U60) will be built as a **separate model, under its own separate plan**, not merged into this portfolio, if and when it is pursued. The reasons are structural, not merely a scope preference: (1) every capability here is read-only inference with no side effects — the transactional surface requires durable state machines, idempotency, and reconciliation against live backend systems, a fundamentally different engineering pattern where a model's accuracy cannot substitute for correct transactional guarantees (a timeout after a payment succeeds but before the model sees the response is a real failure mode no amount of model quality fixes); (2) the mistake cost is categorically higher — a bad Commerce-Rank result is a worse-ordered list, a bad refund/cancellation action executes against real money and real inventory; (3) it has no public-dataset path the way every capability in this portfolio does — the dossier's own use-case entries for U31–U60 are almost uniformly "owned/first-party data required, no public corpus adequate for production assumed," meaning it cannot clear this plan's own two-part gate (§2e) the way Query/Understand/Match/Retrieve/etc. can from day one. Keeping it fully separate protects this portfolio's evidentiary bar from being diluted by a surface that structurally cannot meet it yet, rather than bolting on a permanently under-evaluated extension.

## 0. What changed after reading the full 5,777-line dossier (not just its shorter companion plan)

An earlier pass of this document was written after reading `Commerce_SLM_Research_Plan.md` in full but only sampling the first ~150 lines of the broader dossier before it errored out on size. A full read-through (via a dedicated review pass) surfaced material the earlier version missed entirely. Corrections folded into the sections below:

1. **Commerce-Taste is not fully blocked — it was wrongly marked "no dataset exists."** The dossier names **Amazon-M2** (ch. 6, ch. 32) as a public starter dataset for session/next-item recommendation and cold-start, and **DeepAffinity** (SmolLM2-135M + category heads, beats Gemini 1.5 Flash on proprietary fashion attribute-affinity prediction) as direct small-model architecture evidence. License terms for Amazon-M2 still need verification before commercial use — this is a starting point, not a cleared dataset. Updated in §1b/§7.
2. **Commerce-Agent was missing three directly relevant public benchmarks**: **Tau2-bench** (service-agent environments incl. retail workflows), **BFCL/Gorilla** (function-calling accuracy), **WebShop** (shopping-agent environment). Also missing a sharp, load-bearing distinction the dossier makes explicit (its benchmarks chapter): **pass@k vs. pass^k** — a purchase workflow needs *repeatable first-attempt correctness* (pass^k: succeeds every time, not just once after retries), and conflating the two overstates readiness. Added to §7's Agent row.
3. **Additional named model candidates not in the earlier version**: **GLiNER2-base (205M)** — the dossier repeatedly positions this as the *mandatory* first baseline to beat before building a decoder for any extraction-shaped task (Understand, Match), not an optional comparator. Also **RexBERT** (commerce-pretrained encoder, beats ModernBERT-large on product-title masked-token recovery — evidence for representation quality, not a downstream extraction/matching benchmark by itself), **Marqo ecommerce/fashion embeddings**, **BGE-M3**. Folded into §4/§5/§6/§7 as required baselines/challengers.
4. **New licensing landmines beyond what was already known** (Shopping Reasoning Bench gated/noncommercial, EcomEval access unverified — both already flagged), now confirmed by a direct read of the dossier's full dataset inventory (ch. 11, D01–D40), with its exact verbatim language quoted here rather than paraphrased, since the precision matters: **Amazon Reviews 2023** (D06) — "commercial permission not established; maintainer cannot assign source rights." **MAVE** (D03) — labels/code available but "Amazon source metadata acquired separately," not a self-contained cleared corpus. **Dress Code** (D25) — "request and signed agreement; maintainer states not released to private companies." **ECInstruct** (D02) — CC-BY-4.0 card but requires "underlying source review," not blanket ingestion. **Three additional landmines found in this direct read, not previously flagged in this plan**: **ModCloth/RentTheRunway fit data** (D22) — "research download links; commercial permission not established" — relevant if Commerce-Bundle or a future fit-assistance feature ever reaches for this. **DeepFashion2** (D26) — "no commercial clearance established." **SKU-110K** (D40) — "academic and non-commercial dataset use" per the author repository. None of these are currently in this plan's named datasets (ABO/ESCI/WANDS/Amazon-M2), but all six are now explicit do-not-reach-for-this-as-a-shortcut flags, particularly for Bundle/Taste/QA later, where an unnamed dataset gap might otherwise tempt someone to grab whatever's easiest to find.
5. **The retention-regression gate (§2b) was incomplete**: the dossier's forgetting chapter (ch. 34) gives the formal apparatus this plan was missing — confirmed by a direct read: an `A[t, j]` matrix (performance on task *j* after training stage *t*), **backward transfer** = mean over earlier tasks of `A[T,j] - A[j,j]`, and **forgetting** for each earlier task = `max over s from j through T-1 of A[s,j] minus A[T,j]` — and states explicitly that retention must be re-checked **after preference/RL tuning, after adapter merge, AND after quantization**, not just once after SFT. The earlier version of §2b only specified a post-SFT check; now fixed. **Two further additions from the direct read, not previously captured:**
   - **Four distinct regression types to diagnose separately, not lump together**: parameter interference (the actual weight-level forgetting this plan already targets); a data/policy change (e.g., the catalog's return policy changed — do not "fix" a model that's now correctly reflecting an old, obsolete policy by retraining it back onto stale data); a deployment transformation (BF16→INT4 quantization changing behavior, already covered by §2b's post-quantization check); and a system change (retrieval index version or tool schema drift breaking a previously-correct model's inputs, not the model itself). A capability that appears to regress must be checked against all four before assuming it's weight-level forgetting requiring a retrain.
   - **Exact replay-screening protocol**: when using replay data to fight forgetting (already recommended in this plan as the default first mitigation), screen at **5%, 10%, and 20% replay as a share of supervised tokens, not example count** — and report both a fixed-total-token-budget track and a fixed-new-task-exposure track separately, since conflating the two "can make retention appear free" when it is actually trading away new-task training volume.
6. **The "beats frontier models" claim (§2d) was under-specified**: the dossier (its ch. 22) distinguishes three separate claims that require different experiments — a **model claim** (same inputs/tools, more correct outputs), a **system claim** (the full application wins due to retrieval/validation/routing, not the model alone), and an **economic claim** (same quality, lower cost/latency). The shipped README's own claims are actually a mix of model-claim (QueryNER benchmark) and economic-claim (cost comparison) evidence, presented together without this distinction — every new capability must now state which claim it's making. Fixed in §2d below.
7. **The 3/n statistical bound (§2c item 2) was missing a caveat the dossier states explicitly**: real failures may be *correlated* (same product family, same merchant, same session), which the independent-trials assumption behind 3/n does not account for — the bootstrap must be clustered by product-family/merchant/session, not run as an ordinary per-example resample. Fixed in §2c below.
8. **The sibling-adapter-vs-separate-model decision rule (§2b) gets a cleaner general test from the dossier's ch. 28**: "A category adapter is justified when the shared model has persistent errors on that category after data balancing and schema improvements, and an adapter improves held-out performance enough to pay for serving complexity" — added as the explicit cost-benefit test behind the existing decision-order language.

Separately, a critical review of this plan's own drafting (checked against the actual repo files, not just the dossiers) found and fixed three factual errors: the QueryNER split actually available locally is train (7,841) + test (993) only — no validation split (871) was ever pulled into this repo, that number is dossier-only; ESCI is license-vetted in the dossier's text but nothing is pulled onto disk yet (was wrongly described as "already... in `research/`"); and Commerce-Match's actual schema in `schemas/retrieval_match.py` has only **4** classes (`EXACT_MATCH, SUBSTITUTE, COMPLEMENT, IRRELEVANT`) against the user's specified 5-class target (same/variant/substitute/complement/unrelated) — the schema is missing a distinct "variant" class separate from "same product," which is real schema work to add, not a training-data gap. All three fixed below.

> **Top-line project rule, confirmed by the user, overrides convenience in every section below:** the shipped Commerce-Query model (step-750 adapter, published at `huggingface.co/arghya2030/commercecore-qwen3-1.7b`) must not degrade — not "should try not to," must not. If extending a capability onto the shared base ever risks that model's measured performance, the answer is a **separate model**, full stop. A separate model is a fully acceptable, expected outcome here, not a fallback to be embarrassed about. See §2b for the exact mechanics (frozen artifact, regression gate, decision order).

## 1c. No redundant models: shared architecture choice is fine, shared checkpoint claim is not

Confirmed requirement: don't end up with multiple similar-but-not-quite-distinct models doing near-identical jobs. The rule that resolves this without contradicting §2b's "separate model when needed" guidance: **reusing the same base architecture across capabilities (e.g., Qwen3-0.6B for both Match and Bundle, per §1b) is fine and expected — reusing the same *trained checkpoint* to cover two capabilities' claims is not.** Concretely:

- Match and Bundle may both start from Qwen3-0.6B, and Bundle may even warm-start from Match's trained weights (§1b) — but Bundle is still its own fine-tuned checkpoint, evaluated on its own eval sets, clearing its own §2d bar independently. It is never "Match's checkpoint, relabeled" or "Match's checkpoint, un-retrained, presented as also solving Bundle."
- If two capabilities' eval sets and required outputs turn out to be so close that one trained checkpoint genuinely solves both at the accuracy bar required (measured, not assumed), that is a signal to **merge them into one named capability** in the plan, not to silently ship duplicate near-identical models under two different names. Any such merge is a plan revision, decided from measured overlap, not a shortcut taken during implementation.
- This applies to comparators too, not just CommerceCore's own models: don't run near-duplicate frontier baselines and count them separately (e.g., don't treat "GPT cheap tier" and "GPT cheap tier, slightly different prompt" as two distinct baseline points) — the baseline matrix in §2c item 3 is a fixed, small set precisely so results stay comparable across capabilities.

## 2. Design constraints carried over from the research dossier

These aren't new rules — they're the dossier's own findings, which apply directly to every new capability below:

1. **One shared base model, typed contracts, but sibling adapters by default — not a resumed/joint adapter by default.** The dossier's core thesis (§5–7 of the research plan) is a shared Qwen3-1.7B, with per-task adapters compared against joint training via measured ablation, not assumed. Given the shipped model's own retention near-miss (see §2b below), the safer default here is: same frozen Qwen3-1.7B base, but each new capability gets its **own sibling LoRA adapter**, never a continuation of the existing shipped adapter. A single joint adapter is a later, deliberate ablation — gated by the regression check in §2b — not the starting point. This applies to Understand, which fits the 1.7B band; Match/Retrieve/Rank need a genuinely smaller or different-architecture model regardless (embedding/reranker, or a sub-1B encoder — not a LoRA choice on the 1.7B base at all).
2. **Retrieval is not "generate product IDs from weights."** Commerce-Retrieve and Commerce-Rank need an index (BM25 + dense + reranker) per §6 of the research plan. The model's job is producing embeddings/scores/typed judgments that plug into that index, not memorizing a catalog.
3. **Evidence-gated outputs.** Every new capability must distinguish `supported` / `contradicted` / `unknown` / `not_applicable` per the common representation (§5). No capability may infer a fact (allergen-safe, waterproof, compatible) from absence of evidence.
4. **Same failure-disclosure standard as the shipped README.** Every new capability's writeup must include a real baseline comparison (frontier API + unfine-tuned open model of similar/larger size), a held-out eval, and an explicit "what this is not / where it fails" section — this is what made the Commerce-Query release credible, and it's the bar the next capability is held to.
5. **Reuse before build.** Before training anything new, check whether the existing Commerce-Query adapter's representations already cover part of the new task (e.g., Commerce-Rank likely reuses constraint-satisfaction output from Commerce-Query as a hard-filter feature) — do not duplicate a capability that composition of existing pieces already provides.

## 2b. Non-negotiable rule: the shipped Commerce-Query model must not regress

This project already has one documented near-miss with this exact risk: in the original training run, the final checkpoint (step 1200) had *worse* retention (0.489) than an earlier one (step 750, retention 0.614), which is exactly why step 750 — not the final step — was selected as the shipped artifact (`train/results_multitask_clean/MODEL_SELECTION_DECISION.md`). Expanding capabilities must not casually reopen that risk. Two concrete protections, both mandatory, not optional:

1. **The shipped step-750 adapter and merged model directory are frozen artifacts.** No new training run resumes from them or overwrites them in place. `models/commercecore_merged_step750/` and the adapter that produced it stay exactly as published. Every new capability trains as either (a) a **new sibling LoRA adapter on the same frozen Qwen3-1.7B base**, loaded independently at serve time alongside the existing one, or (b) if a joint multi-task adapter is later desired, a **new training run from the frozen base with all tasks mixed from step 0** — never a continuation of the existing run.
2. **Any joint run must pass a regression gate against the current shipped numbers before it can replace anything, checked at every stage that can change behavior — not just once after SFT.** The current numbers are the floor, not the base model's numbers: constraint F1 0.725, QueryNER F1 0.556 (both at step 750, per the README and `MODEL_SELECTION_DECISION.md`). Before accepting any new checkpoint that touches Commerce-Query's task at all, re-run the existing `eval/full_queryner_eval.py` and the held-out constraint eval against it. Apply the same threshold the dossier already prescribes for retention (research plan §10): **max 1 percentage-point drop**, else reject the checkpoint and keep serving step 750. **The broader dossier's forgetting chapter (ch. 34) makes explicit what the earlier version of this rule missed: retention can regress after preference/RL tuning, after adapter merge, and after quantization — not only after the initial SFT run.** Re-run this same gate at each of those points, not just once: (i) post-SFT, (ii) post-DPO/RL if used, (iii) post-merge into a single artifact, (iv) post-quantization for serving. Track results in a per-stage-per-task matrix (`A[stage, task]`), the same shape the dossier specifies, so a regression introduced at merge or quantization isn't hidden by a good post-SFT number.
3. **Retention checking runs concurrently with training, at every checkpoint, against the public benchmark and the frontier-LLM reference — not as a separate before/after step tacked on afterward.** Confirmed requirement: the shipped model's own checkpoint-eval log already does this correctly for its own task (every 150 steps, both constraint F1 and QueryNER F1 and retention were logged together, in the same table — see `MODEL_SELECTION_DECISION.md`'s checkpoint history). Every new capability must replicate this exact pattern, extended to include the frontier-LLM comparison at each checkpoint, not only at the end:
   - At every evaluation checkpoint during training (every 150 steps, or the equivalent cadence for a non-LoRA/non-1.7B model), log **three numbers side by side, same checkpoint, same eval set**: (i) the new capability's own task metric, (ii) the retention score against the frozen base/prior shipped model on the general/prior-task suite, and (iii) where feasible at that cadence, the standing frontier-LLM reference score on the same public benchmark (this third number does not need to be re-run from the API every single checkpoint if cost is prohibitive — but it must be a fixed, known number recorded in the same table, not omitted, so every checkpoint's task-vs-retention tradeoff is read against the same public-benchmark-and-frontier-model yardstick used for the final release decision).
   - Checkpoint selection (§2b item 1's non-final-checkpoint discipline) must be made by reading all three numbers together at each checkpoint, exactly as the original `MODEL_SELECTION_DECISION.md` did — not by picking the best task-metric checkpoint first and only checking retention/frontier-comparison afterward as a final gate. The original build's own near-miss (step 1200 being worse on retention despite similar task F1) was caught because retention was tracked at every checkpoint, not because it was checked once at the end; do not regress on this practice for new capabilities.
   - For capabilities training as a fully separate model with no shared weights (Match, Retrieve, Rank, Bundle), item (ii) above (retention against the frozen base) is `NOT_APPLICABLE` by construction — but items (i) and (iii) still apply: log the task metric against the public benchmark and the frontier-LLM reference at every checkpoint, not only at the final one, so a capability isn't declared "shipped" based on a lucky final checkpoint that was never compared against the same yardstick earlier in training.
4. **A fully separate model is always an acceptable fallback, not a failure.** If a sibling adapter still measurably interferes when served together with the existing one (e.g., shared tokenizer/KV-cache serving optimizations turn out to blur behavior, or a capability's target size band is genuinely incompatible with the 1.7B base — true today for Retrieve/Rank), train and serve it as an **entirely independent model** with its own weights, its own serving path, and no shared checkpoint at all. This costs more in serving/ops complexity (two model artifacts instead of one, per §14 of the research plan on multi-tenant/multi-model serving) but has the strongest possible guarantee against touching the shipped model's behavior. This is the right default whenever the honest answer to "could this share a checkpoint safely" is "not sure" rather than "yes, measured."

Decision order, cheapest-safe-option first: **(a) sibling adapter, same frozen base** → if that's not clearly safe or the size band doesn't fit, **(c) fully separate model** → only attempt **(b) single joint adapter** later, as a deliberate, gated ablation, once (a) or (c) already work and there's a measured reason to believe joint training adds value beyond convenience. Never start at (b).

**Concrete test for when (b) is actually justified, not just convenient** (the broader dossier's ch. 28 states this generally — applied here to adapters specifically): a joint/shared adapter is justified only when the separate/sibling version has *persistent* errors on its task after data balancing and schema fixes have already been tried, **and** the joint version measurably improves held-out performance enough to be worth the extra retention risk and regression-gate overhead. "It would be simpler to have one checkpoint" is not, by itself, a justification.

Default recommendation given this constraint: **build Commerce-Understand as a sibling adapter (a)** — it fits the 1.7B band and is low-risk. **Build Commerce-Match as a separate small model (c) from the start** — its 150–500M target band is already below the 1.7B base, so there's no ambiguity to resolve; don't force it onto the shared backbone just to keep one checkpoint. Only attempt a single joint adapter (b) later, as a deliberate ablation with the regression gate in place, once there's a measured reason to believe joint training helps (per the dossier's own required ablation, research plan §13: "single-task vs joint SFT... does shared learning help beyond deployment convenience?"). Don't assume joint training is free — it's the thing that already cost you retention once.

## 2c. Robust evaluation — mandatory for every capability, including the regression gate itself

The README's own history is the argument for this section: the headline Commerce-Query numbers (beats every tested frontier model on QueryNER and the held-out set) did **not** hold on a small, deliberately harder fresh-query test — Claude Sonnet 5 and GPT's cheap tier both won there instead. That gap wasn't caught by the primary benchmark; it was only caught because a second, independent, harder eval was run afterward. Every capability in this plan — including the regression gate in §2b — inherits that lesson. A single benchmark number, however good, is not evidence of robustness by itself.

Minimum bar, per capability, before it can be called "shipped" (not "trained" — trained and evaluated are different claims):

1. **At least two eval sets per capability, not one**: (i) a held-out split of the training-distribution data, and (ii) an independent, harder, out-of-distribution set built or selected specifically to stress the capability's known failure modes — negation, multi-clause/multi-constraint inputs, unit conversion, unseen taxonomy/schema, partial evidence. For Match/Rank/Retrieve, WANDS is already earmarked as this out-of-distribution set (§1b) precisely because it's a different retailer's taxonomy — do not let it leak into tuning at any point, including hyperparameter selection. **Minimum size per set: at least 300 adjudicated cases**, matching the dossier's own stated floor for a defensible error-rate bound (§12) — a smaller set cannot support any "beats X" or "safe" claim below, whatever the point estimate says.
2. **Confidence intervals on every headline number, not point estimates.** The existing QueryNER result already does this correctly (bootstrap 95% CI, 10,000 resamples, full 993-example test set) — replicate that exact method for every new capability's primary metric, not just the total set. For the release/regression-gate threshold specifically, use the dossier's own stated bound (research plan §12): for zero observed errors in *n* accepted cases, the rough 95% upper error bound is 3/n — a few hundred passing cases cannot support a "near-perfect" claim, so don't write one. **This 3/n bound assumes independent trials — the broader dossier is explicit that real failures are often correlated (same product family, same merchant, same session), which breaks that assumption.** Cluster the bootstrap resample by product-family/merchant/session, not by individual example, whenever cases share one of those groupings; report the clustered interval, not the naive per-example one.
3. **Baseline matrix, every time**: frontier API (cheap tier + flagship, at least one from each of two providers, matching the already-established GPT/Claude pattern) + an unfine-tuned open model at equal-or-larger size + the dossier's named non-generative baseline where one exists (ModernBERT and **GLiNER2-base** for intent/NER/extraction-shaped tasks — GLiNER2-base specifically is the broader dossier's *mandatory* first bar to clear before building a decoder for Understand or Match, not an optional comparator — plus NuExtract for catalog extraction, per research plan §7). A capability is not "beating the baseline" until it's beaten all of these, not just the ones convenient to run.
4. **Report the failure mode, not just the score.** The existing README's most useful section is the one that reads actual wrong outputs and names the pattern (drops constraints past 2, doesn't normalize unseen vocabulary, mishandles negation) rather than stopping at an aggregate F1. Every new capability's eval writeup needs that same paragraph — read a sample of the actual failures by hand before declaring the capability done, the same way the "products with X" template problem in the original synthetic data was only caught by manual inspection, not by any automated gate (README, "Challenges faced in training," item 2).
5. **Regression gate is itself evaluated at the same rigor, not just a single before/after diff.** Re-running `eval/full_queryner_eval.py` once and comparing two point numbers is necessary but not sufficient — use paired bootstrap resampling on the same query set (same method as item 2) so the "max 1 point drop" threshold in §2b is judged against a confidence interval on the *difference*, not two noisy point estimates that could cross the threshold by chance in either direction. Per §2b, run this at every stage (post-SFT, post-DPO/RL, post-merge, post-quantization), not once.
6. **No held-out set may be re-used as a decision input for template/hyperparameter/prompt selection.** This is the dossier's own repeated instruction (research plan §9 step 3, §12): do not tune against the eval set. If a set has been looked at to make a modeling decision, it is no longer held-out — freeze a new one rather than treat a compromised set as still valid.
7. **Report actual cost, at the same granularity as the shipped README's cost table** ($0.02 hardware profiling / $0.23 debug run / $0.90 full training run / ~$1.00 synthetic data / ~$3–5 baseline comparisons / ~$1–2 pod overhead = ~$6–9 total). Every new capability's writeup needs an equivalent itemized breakdown, not a single rolled-up number — this is what let the original build's own honest cost-comparison section (self-hosting vs. GPT cheap tier) actually be checked and corrected once already.
8. **Serving smoke-test on both GPU and local CPU before calling a capability "shipped."** The original build caught three real serving bugs this way (an unconditional `peft` import breaking the no-adapter case, a Python/transformers version mismatch only visible on a second machine, hardcoded pod-only file paths in eval scripts) — none of which showed up in training or offline eval. Every new separate-model artifact (Match, Retrieve, Rank, Bundle) needs its own equivalent smoke test in a fresh environment before being called done, not just a passing eval script run on the training pod.

## 2d. Acceptance bar: beat the frontier models on every capability's own task — not just "compare"

Confirmed requirement: for each capability, the trained model must **outperform** the same baseline matrix from §2c item 3 — including Claude and GPT, both cheap and flagship tiers — on that capability's own eval sets, not merely be evaluated alongside them. This is the same bar the shipped Commerce-Query model already met on its primary benchmarks (README: "beats every tested frontier tier, cheap and flagship, from both providers"). "Outperform" here means a win under the same paired-bootstrap confidence interval used in §2c item 2 — a higher point estimate whose CI still overlaps the baseline's is not a claimed win, it's a tie to be reported as a tie.

**State which of three distinct claims is being made, since each needs a different experiment** (the broader dossier's ch. 22 makes this explicit, and the shipped README already mixes two of these without naming them): a **model claim** (same inputs/tools available to both systems, CommerceCore's output is more correct — this is what the QueryNER/held-out benchmark numbers actually show); a **system claim** (the complete application — model plus retrieval, validation, routing — wins, which is a claim about more than the checkpoint alone); and an **economic claim** (equal or acceptable quality at materially lower cost/latency — this is what the README's token-cost comparison actually shows, and where it honestly discloses GPT's cheap tier winning on raw cost). Every new capability's "beats frontier models" writeup must say explicitly which of these three claims it is making, since a reader conflating a model-claim benchmark with a system-level product claim is exactly the kind of overstatement this project has otherwise been careful to avoid.

Two things follow directly from the existing README, and must carry forward exactly as-is, not get quietly dropped under pressure to hit this bar:

1. **The bar is task-specific, not general-capability.** Commerce-Query's win is real and measured on constraint extraction and QueryNER-style segmentation — it says nothing about general reasoning, and the README is explicit about that ("Not 'beats Claude/GPT' in general"). Every new capability's "we beat frontier models" claim must carry the same scope limit in its own writeup: beats them *at this narrow task*, on *this measured eval*, full stop.
2. **A capability that does not clear this bar is not shipped as "the best system for this task."** It can still ship as a valid *cost/deployment* choice (self-hosted, private, cheaper at volume — the same honest framing the README already uses for the raw-token-cost comparison, where GPT's cheap tier actually wins on cost alone). What must not happen: quietly weakening this bar, or reporting only the eval subset where the trained model wins, once a capability turns out to underperform Claude/GPT on its harder or out-of-distribution set — exactly the situation the existing README already discloses openly for Commerce-Query's own fresh-query test (Claude Sonnet 5 and GPT cheap tier beat it there). 3. **This bar applies per capability, independently** — a strong result on Commerce-Understand does not exempt Commerce-Match from clearing its own bar on its own eval sets. Each of the nine rows in §1b earns its "beats frontier models" claim (or its honest "does not, here's the disclosed gap" writeup) on its own measured evidence.

**Bundle and Agent are the two capabilities where synthetic data will necessarily be the majority of training volume, not a minority augmentation.** That is disclosed here explicitly, not hidden inside a generic "synthetic data is fine if gated" statement — a capability trained mostly on synthetic data needs a correspondingly larger, harder adversarial fixture set (see below) before it can be trusted, and its writeup must say plainly that it lacks a public-dataset backbone, not imply parity with Query/Understand/Match/Retrieve/Rank/Taste.

**The four-property gate, reused exactly from the shipped model's own `validators/mechanical_validator.py` and `validators/adversarial_fixtures.py`, mandatory for every capability's synthetic data, no exceptions:**

1. **Schema validity** — parses into the expected typed structure. Mechanical, cheap, necessary but not sufficient by itself.
2. **Source-span binding** — every cited evidence span is a verbatim substring of the source text at its claimed offset. Proves binding, not meaning — a span can be perfectly bound while supporting a false conclusion (the shipped project's own documented example: citing "cotton" as evidence from "contains no cotton" passes this check while being backwards).
3. **Execution correctness** — given the generated output (which may itself be wrong), does executing it against a synthetic catalog/simulator resolve consistently with what it claims. Checks internal consistency, not truth.
4. **Naturalness / semantic fidelity** — the hardest one, and the one the earlier build actually got wrong once: an automated pass on properties 1–3 is not proof of real-world quality. The shipped project's own history is the exact cautionary case: 70% of an early synthetic batch (313/450 rows) passed every mechanical check while using a generic "products with X" template — caught only by a person reading the actual generated text, not by any automated gate that existed at the time. **Do not treat properties 1–3 passing as "the data is good."** Every new capability's synthetic-data pipeline must include: (a) a mechanical naturalness proxy (a living blocklist of generic template phrases, extended as new patterns are found — start from the existing `GENERIC_TEMPLATE_PHRASES` list in `validators/mechanical_validator.py` and add capability-specific patterns), and (b) a **mandatory manual spot-check of a real sample** (minimum 10% of any new synthetic batch, or 50 rows, whichever is larger) before that batch is accepted into training — read the actual text, not just the pass/fail flags.

**Independently-authored adversarial fixtures, mandatory per capability**, following the shipped project's own pattern exactly (`validators/adversarial_fixtures.py`): fixtures are hand-written by someone who did not build the generation pipeline being tested, specifically to demonstrate cases where properties 1–3 all pass while the output is semantically wrong. Minimum required categories per capability, reusing the categories already established plus capability-specific extensions:

- **Negation** (existing category — reuse directly): "no added sugar," "not compatible with," "unrelated to," etc. — substring-true, meaning-false traps.
- **Omitted constraint / omitted attribute** (existing category — reuse directly): a multi-requirement source where the generated output silently drops one.
- **Units mismatch** (existing category — reuse directly): unit or currency conversion errors that look plausible.
- **Conflicting facts** (existing category — reuse directly): contradictory source statements (already known to have caused a real generation-time crash in the original build — catch these as an expected reject-and-retry case, not a fatal error, same as before).
- **Missing field** (existing category — reuse directly): a field absent from source text that must resolve to `unknown`, not a guessed value.
- **Capability-specific additions**: Match/Bundle need a **same-vs-variant confusion** fixture category (per §5); Retrieve/Rank need a **partial-match-scored-as-full-match** fixture category; Agent needs a **pass-once-but-not-repeatably** fixture category (surfacing the pass@k vs. pass^k gap from §7); Understand needs a **plausible-but-uncited-attribute** fixture category (a value that's true of the product category in general but not stated for this specific listing).

Training data: owned query reformulations and successful search sessions (first-party, per the dossier's own U12 entry — no adequate public dataset is named for this specific task), plus ESCI as an adjacent relevance-pair signal for validating that a rewrite actually improves retrieval rather than drifting the query's meaning. Public benchmark gate (§2e): none currently assigned — the dossier states "no direct matched quantitative result verified" for U12 — this is a disclosed gap requiring a new benchmark decision before this sub-capability can claim to have cleared the two-part gate, same treatment as Commerce-Bundle's compatibility half. Evaluation must include the dossier's own required metrics for this task: constraint preservation rate, retrieval recall gain from the rewrite, wrong-brand drift rate, and a zero-result guardrail (a rewrite must never be allowed to produce a worse or empty result silently).

Add this to the priority ordering as an extension of Rank 1 (Commerce-Understand) work, since both are sibling-adapter additions to the same frozen base and can share the same regression-gate infrastructure being built for Understand — but track it and evaluate it as its own distinct sub-capability with its own eval sets, not folded silently into Commerce-Query's existing benchmark numbers.

## 3. Priority order for the next capabilities

Ranked by (a) how much they reuse what's already shipped, (b) dossier-stated priority (§1 of the research plan: query understanding → catalog understanding → matching → recovery), and (c) how directly they unblock a real, testable product loop (search that actually returns ranked, filtered products, not just parsed intent).

| Rank | Capability | Why this order |
|---|---|---|
| 1 | **Commerce-Understand** | Schema already exists; 180 examples already collected; this is "finish what's half-done," not new scope. Directly required before Commerce-Match or Commerce-Rank can have real catalog facts to check constraints against. |
| 2 | **Commerce-Match** | Schema exists (needs one class added, see §5); ESCI (E/S/C/I labels) is license-vetted in the dossier's text and identifiable today, though not yet pulled onto disk — a real public dataset is available to fetch. Needed before Rank (rank needs match/relevance signal) and before Bundle (bundle needs complement vs. substitute vs. unrelated, which is a superset of Match's job). |
| 3 | **Commerce-Retrieve** | Needs Commerce-Query (done) and Commerce-Understand (candidate #1) to have typed queries and typed catalog entries to index. This is the first capability that produces an actual searchable system, so it's the first "product demo" milestone. |
| 4 | **Commerce-Rank** | Needs Retrieve's candidate list and Match's relevance judgments as direct inputs — cannot be usefully trained before both exist. |
| 5 | **Commerce-Bundle** | A specialization of Match (complement/compatible detection) plus a compatibility graph; do after Match is proven, since it reuses Match's relation head. |
| 6 | **Commerce-Agent** | The dossier explicitly gates this: "Priority 4 [recovery/tools] is enabled only after trustworthy extraction and matching exist" (§1). Needs Query + Understand + Match + Retrieve all working first, since a tool plan calls into all of them. |
| 7 | **Commerce-Taste** | Requires session/user history data this project has never collected (no user-behavior dataset exists in the repo or the dossier's data sources list, §8). Highest data-acquisition cost of any capability here. |
| 8 | **Commerce-QA** | Explicitly marked ★★★ (lowest of the nine) and is the dossier's own "separate projects" category boundary (§1: "personalized recommendations... are separate projects" — QA-over-reviews is adjacent to that boundary). Largest target size (1–3B) for the smallest stated importance; do last. |

Rank 1–3 are laid out below in enough detail to start immediately. Rank 4–8 get a shorter scoping section each, to be expanded into their own detailed plan once 1–3 ship (matching the existing repo's own `plans/00_shared_core.md`-first pattern).

## 4. Rank 1 — Commerce-Understand: finish the half-built capability

**Target:** 0.5–1.5B — reuse the existing Qwen3-1.7B backbone (already inside target band), do not spin up a separate model.

**What exists today:** `schemas/catalog_taxonomy.py` (contract), 180 synthetic examples used only as auxiliary training signal in the Commerce-Query run, zero dedicated eval.

**Gap to close:**
1. Dedicated eval set, held out from anything used in the original 2,130-example multitask run (check `train/build_multitask_mixture.py` for exactly which 180 rows were used, so the new eval set is disjoint, not just relabeled).
2. Expand training data using the dossier's actual recommended sources (§8, §9 of research plan): Amazon Berkeley Objects (147,702 listings, CC BY 4.0, already identified as "primary product-text/type/attribute corpus") — not yet pulled into this repo's `data/` directory (only `data/queryner/` exists today).
3. Train/evaluate as its own checkpoint-selection decision (same MODEL_SELECTION_DECISION.md pattern used for Commerce-Query), reporting field-level micro/macro F1 and — critically, per the dossier's evidence-state rule (§5) — **missingness accuracy**: does the model correctly emit `unknown` for a field absent from source text, rather than hallucinating a value? This is the single most important metric this capability needs and the one most likely to be silently wrong if skipped.
4. Baseline comparison against **GLiNER2-base (mandatory first bar, per §0/§2c)**, NuExtract (both already named as required comparators in the dossier's model table, §7) plus frontier API, matching the rigor of the Commerce-Query README.
5. **Reuse the exact QLoRA settings that already worked**, as the starting point, not a re-derivation: NF4 double-quant, BF16 compute, LoRA r=16/alpha=32/dropout=0.05, paged AdamW 8-bit, LR 1e-4 (research plan §10, and the shipped model's own actual run). Only deviate from these if a smoke-run shows a specific reason to.

**Concrete first milestone:** a `train/results_understand/` directory with the same file shape as `results_multitask_clean/` (loss log, checkpoint eval log, retention log, MODEL_SELECTION_DECISION.md) and a README section with the same "beats/loses to X" honesty as the current one, including which of the three claim types (§2d) is being made.

## 5. Rank 2 — Commerce-Match: same/variant/substitute/complement/unrelated (5-class target)

**Target:** 150–500M — this is smaller than the current 1.7B backbone; test whether a distilled/smaller checkpoint (Qwen3-0.6B, already in the dossier's shortlist §7 as the "compression challenger") hits acceptable accuracy before defaulting to the 1.7B shared adapter. This capability is the first real test of whether a smaller sibling model pays off.

**What exists today:** `schemas/retrieval_match.py` — contract only, and **incomplete against the target**: its `RelationClass` enum currently has 4 values (`EXACT_MATCH, SUBSTITUTE, COMPLEMENT, IRRELEVANT`), not the 5 the user specified (same/variant/substitute/complement/unrelated). ESCI dataset identified and license-vetted in the dossier's text, but not yet pulled anywhere onto disk in this repo.

**Gap to close:**
1. **Schema fix, before any data work:** add a distinct `VARIANT` class to `RelationClass` in `schemas/retrieval_match.py`, separating "same product" (`EXACT_MATCH`) from "same product, different variant" (new `VARIANT` — e.g., different size/color of the identical SKU family). This is new schema work, not a training gap — the earlier version of this plan wrongly described this as an existing 5-class schema.
2. Pull Amazon ESCI (~130k queries / 2.62M judgments, Apache-2.0, license-vetted in the dossier's text) into `data/esci/`, matching the same audit rigor already applied to QueryNER in this repo (split integrity check, cross-split duplicate check, label distribution report).
3. **Important labeling gap the dossier flags explicitly (§9, step 4):** ESCI's E/S/C/I labels are *not* the same taxonomy as the 5-class target. E→same-or-variant, S→substitute, C→complement, I→unrelated is a plausible mapping but is an assumption to validate by hand on a sample before trusting it as ground truth, and **ESCI does not distinguish "same product" from "variant" at all** — that split needs new annotation or a heuristic (e.g., shared parent SKU/GTIN) rather than assuming ESCI covers it out of the box.
4. Train a pair-classification head (query–product or product–product, both needed — Match is used both for query relevance and for Bundle's future complement detection).
5. Eval per the dossier's required slices (§12): accessory-vs-product confusion, compatible-vs-similar, partial evidence cases, **and specifically same-vs-variant confusion given item 1/3 above** — not just aggregate macro-F1.
6. Baseline against GLiNER2-base and ModernBERT-base (§2c item 3) before concluding a generative approach is needed at all.

**Concrete first milestone:** an ESCI-to-Match label mapping document with a manually-audited sample (following the same "read 1,420 rows by hand" rigor already demonstrated on the WDC dataset in the dossier), before any training run starts.

## 6. Rank 3 — Commerce-Retrieve: query/image → correct products

**Target:** 150–400M — smallest target band in the whole table; this is explicitly meant to be a retrieval-specialist size, not the shared 1.7B backbone. Candidate starting points already named in the dossier (§7, §10): Qwen3-Embedding-0.6B (frozen initially) as the dense encoder, or the research-variant shared projection head described in §6 ("Research variant: genuinely shared generation and retrieval") as a later ablation, not the v0 default.

**What exists today:** nothing — no index, no embedding model wiring, no retrieval eval harness in the repo.

**Gap to close (this is new infrastructure, not just new training data):**
1. Stand up the BM25 + dense + fusion pipeline the dossier specifies exactly (§6 table): BM25 in the merchant's engine, Qwen3-Embedding-0.6B dense candidates, reciprocal rank fusion k=60. This is retrieval *infrastructure*, separate from any model fine-tuning — build this before training anything.
2. Wire Commerce-Understand's output (once it exists, rank 1) as the indexed catalog representation, and Commerce-Query's output (already shipped) as the query-side representation — this is the first capability that actually composes the other two, which is the point of the shared-contract design.
3. Evaluate on WANDS (480 queries / 42,994 products, MIT, already vetted §8) as the **held-out generalization test**, per the dossier's explicit instruction: "hold out entirely during tuning." Do not tune against it.
4. Full-corpus retrieval eval, not just reranking of pre-judged candidates — the dossier is explicit (§12) that these are two different experiments and conflating them overstates recall.

**Concrete first milestone:** a working `retrieve/` module that takes one Commerce-Query output + one indexed catalog slice and returns a ranked candidate list with RRF scores, tested end-to-end on a small (~1,000 product) slice of ABO before scaling up.

## 8. What NOT to do (carried forward from the dossier, still applies)

- Do not train a new foundation model per capability. Default to the shared Qwen3-1.7B adapter approach that already works for Commerce-Query; only break into a smaller specialist model where the target size band genuinely requires it (Retrieve, Rank, Match all have sub-1B targets for good reasons — latency and index-cost, not capability limits).
- Do not claim a new capability "works" without the same rigor the shipped README already set: real held-out eval, real frontier-model baseline, disclosed failure modes. The existing README's honesty about the fresh-query regression (Commerce-Query loses to Claude Sonnet 5 and GPT cheap tier on harder phrasing) is the standard, not an exception.
- Do not let a new capability's training data quietly leak into another capability's held-out set — this repo already has the discipline (QueryNER/ESCI overlap check, §9 step 4 of the dossier) of checking cross-dataset ID overlap; apply it every time a new dataset is added.
- Do not infer facts from absence of evidence in any new capability (Understand's `unknown` state, Match's partial-evidence slice, Bundle's compatibility gate) — this is the dossier's single most repeated constraint (§1, §5, §9, §16) and the one most likely to be silently violated under deadline pressure.

## 8b. Lessons from the previous training run — every documented mistake, as a checklist so none repeat

Every item below is a real, specific mistake this project already made once, found in the shipped model's own README, training logs, or the dossier's evaluation chapters — not a hypothetical risk. Each is written as a checklist item to actively verify against on every new capability, not a story to remember passively.

**Data quality — mistakes that passed every mechanical check and were only caught by reading actual output:**
- [ ] Has a real person read a random 10%+ sample of any new synthetic batch, not just checked that it passes schema/span/execution validation? (The shipped model's own early synthetic data: 70% of 450 rows used a generic "products with X" template, passing every mechanical check, caught only by manual reading — §2f's four-property gate exists specifically because of this.)
- [ ] Does the generation pipeline treat a genuinely unrenderable/contradictory scenario (e.g. `contains_nuts=true AND contains_nuts=false`) as an expected reject-and-retry case, with a caught exception — not an unhandled crash that stops a whole generation run?
- [ ] Have independently-authored adversarial fixtures (not sampled from the same pipeline being tested) been written for negation, omitted-constraint, units-mismatch, conflicting-facts, and missing-field cases, per capability, before trusting that pipeline's synthetic output? (§2f)
- [ ] Does the generation pipeline check that the LLM's natural-language paraphrase actually **surfaces** the target label it was supposed to encode — not just that the label was fixed correctly in code before the paraphrase step? **This was the single most common real rejection reason in the shipped model's own generation run, checked directly against its logs**: of 11 total rejected rows in `data/generation_rejects.jsonl`, 10 (91%) were `no_constraint_surfaced_in_paraphrase` — e.g. a scenario correctly encoding `contains_nuts=true`, but the LLM's paraphrase produced "roasted almonds 200g no added sugar," which never actually mentions nuts in a way a downstream model could learn from. The structured-scenario-first method (fixing the label in code before any LLM call, §"The strategy" in the shipped README) prevents the label from being *wrong*, but does not by itself prevent the paraphrase from *failing to express* that label at all — these are different failure modes, and only the second one requires this specific check. Every new capability's synthetic pipeline needs an explicit surfacing-check (does the generated text actually contain evidence for every constraint the scenario encodes, not just schema-valid metadata pointing at it) as its own gate, separate from the four-property gate in §2f.
- [ ] Does the generation pipeline handle a raw unparseable LLM response (extra text, malformed JSON, prose instead of the expected format) as a caught reject-and-retry case, logged with the actual parse error — not a silent record loss or an unhandled crash? (Confirmed in the same reject log: `unparseable_paraphrase_response`, "Extra data: line 2 column 1," correctly caught and logged, not crashed — this is the one thing the original pipeline already got right; keep doing it, don't regress by skipping this handling in a new capability's pipeline because it feels like unnecessary defensive code.)

**Baseline/API measurement — mistakes that silently deflated a real comparison number:**
- [ ] Has every frontier-API baseline call been checked for silent parameter rejection? (The shipped model's own baseline run: `claude-sonnet-5` rejects the `temperature` parameter with an HTTP 400, which silently zeroed out 2 of 3 repeat measurements and deflated a real 0.59 score down to a misleading 0.05 — caught only because the number looked implausibly low and the raw API errors were checked directly, not the aggregate score.)
- [ ] Is every baseline's exact resolved model ID, revision, and call date recorded — not just a display name like "GPT cheap tier," which can silently point at a different underlying model over time?

**Training/retention — mistakes about when and how to check for forgetting:**
- [ ] Is retention checked at every checkpoint during training, not only once at the end? (The shipped model's own near-miss: step 1200's retention, 0.489, was worse than step 750's, 0.614, despite similar task F1 — caught only because retention was logged every 150 steps, not because it was checked once after training finished. §2b item 3 makes this explicit for every new capability.)
- [ ] Is retention re-checked after every stage that can change behavior — post-SFT, post-DPO/RL, post-adapter-merge, post-quantization — not just post-SFT? (§2b item 2, confirmed by the dossier's own ch. 34 formalism.)
- [ ] Before treating an observed regression as weight-level forgetting requiring a retrain, has it been checked against the other three possible causes: a data/policy change making an old answer correctly obsolete, a deployment-quantization change, or a system-side index/schema-version drift? (§0 item 5's four-regression-type distinction.)

**Training-format gotchas — checked directly against the shipped model's own raw training log, not just its summarized results:**
- [ ] Has the actual training log been read for silent framework auto-corrections, not just the final loss curve? (The shipped model's own raw log, `runpod_archive/logs/train_multitask_v2.log`, shows: `` `use_cache=True` is incompatible with gradient checkpointing. Setting `use_cache=False`. `` — the framework silently overrode a setting because gradient checkpointing was on. This happened to be harmless here, but a silent auto-correction is exactly the kind of thing that can quietly change behavior in a way a loss curve alone won't reveal — treat any such line in a new capability's training log as something to explicitly verify was the intended setting, not just an FYI to scroll past.)
- [ ] Before training starts, has a **frozen-base reference output been captured on a small fixed prompt set** (the exact retention-check pattern already used: "What is the capital of France?", "What is 12 plus 15?", etc.) — so retention comparisons at every checkpoint have a real, saved baseline to diff against, not a re-run of the base model after the fact that might not match the exact original environment/settings?
- [ ] Has the raw per-step loss log (not just the every-150-step checkpoint eval) been kept and archived, the same way `multitask_training_loss_log.csv` was — so a future audit can check for loss spikes or instability between checkpoints, not just at the sampled checkpoint boundaries?

**Serving — mistakes that only surfaced when tested in a fresh environment:**
- [ ] Has this capability's serving code been smoke-tested in a genuinely fresh environment (a second machine, a clean virtualenv, a fresh clone) — not just re-run on the same environment that trained it? (The shipped model's own three real serving bugs — an unconditional `peft` import breaking the no-adapter path, a Python/transformers version mismatch invisible until tested on a second machine, hardcoded pod-only file paths in eval scripts — were all found this way, none by training or offline eval. §2c item 8.)
- [ ] Does every new capability's serving config actually support pointing at its own merged/exported artifact by path, not just a base HF model ID — i.e., does the "clone and run" path actually work for someone who isn't the original builder?

**Evaluation rigor — mistakes about what a good-looking number actually proves:**
- [ ] Has this capability's headline benchmark result been checked against a second, harder, independent eval set — not just the primary benchmark? (The shipped model's own fresh-query test: strong QueryNER/held-out numbers did not hold on 6 new, harder queries with negation/unit-conversion/comparative framing — Claude Sonnet 5 and GPT cheap tier won there instead. This was only caught because a second eval was deliberately run; §2c item 1 requires this for every capability from the start, not as an afterthought.)
- [ ] Does every "beats X" claim state which of the three claim types (model/system/economic, §2d) it actually is — not a blended claim that reads as stronger than what was measured? (The shipped model's own cost-comparison section initially stated self-hosting was cheaper, which was wrong and had to be corrected once already — self-hosting only wins past a real, stated breakeven volume, not universally.)
- [ ] Is the 3/n (or similar small-sample) statistical bound being applied with product-family/merchant/session clustering, not treated as independent per-example trials? (§0 item 7, §2c item 2 — correlated failures break the naive bound.)

Pull ABO into `commercecore/data/abo/` with the same audit rigor as the existing QueryNER ingestion, build a disjoint eval set, and reuse `train/train_multitask.py`'s checkpoint-selection pattern rather than writing a new training script from scratch.
